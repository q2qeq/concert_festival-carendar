# 공연캘린더 — 내한공연·페스티벌 일정 캘린더

Astro 정적 사이트. 해외 아티스트 내한 공연/페스티벌 일정을 D-day 형태로 정리해서
보여주는 유틸리티형 콘텐츠 사이트입니다. "블로그 글쓰기"가 아니라 "정보를 정확하게
정리해서 보여주는 것" 자체가 핵심 가치라, 애드센스 스케일드 콘텐츠 어뷰징 정책 리스크가
순수 블로그보다 훨씬 낮습니다.

## 왜 티켓 사이트를 크롤링하지 않았나

사이트를 만들면서 인터파크 티켓(`ticket.interpark.com`)의 robots.txt를 확인해보니
크롤러 접근 자체를 금지하고 있었습니다. 다른 티켓 사이트(YES24, 티켓링크)는 robots.txt
자체는 상대적으로 느슨하지만, robots.txt와 별개로 각 사이트의 이용약관에 자동 수집을
제한하는 조항이 있을 가능성이 높습니다. 상업적 티켓 플랫폼을 무단으로 크롤링하는 건
법적/약관 리스크가 있고, 막히면 사이트 전체가 흔들리는 불안정한 데이터 소스이기도 합니다.

대신 **KOPIS(공연예술통합전산망)** — 문화체육관광부 산하 예술경영지원센터가 운영하는
공식 공개 데이터 서비스 — 를 1차 데이터 소스로 잡았습니다. 콘서트 장르 데이터를 포함하고
있고, 무료로 API 키를 발급받을 수 있는 정부 공식 오픈 API라 법적 리스크가 없습니다.

## 데이터 소스 구성

1. **KOPIS Open API (권장, 자동화)**: `scripts/fetch-kopis.mjs` 스캐폴드가 있습니다.
   - `https://www.kopis.or.kr` 에서 OpenAPI 메뉴로 가서 무료 서비스키를 발급받으세요.
   - `.env.example`을 `.env`로 복사하고 `KOPIS_SERVICE_KEY`를 채운 뒤 `npm run fetch:kopis`
     실행.
   - **2026-08-27 업데이트**: 실제 발급받은 키로 API를 직접 호출해서 검증했습니다.
     `shcate=CCCD`가 "대중음악(콘서트)" 장르의 실제 코드입니다 (처음 넣었던 `BBBF`는
     같은 조건에서 빈 결과만 나와서 틀린 값이었음을 확인 - 수정 완료).
   - **커버리지 한계**: KOPIS는 국내 아티스트/페스티벌/재즈 공연은 잘 잡지만, Post
     Malone·Charlie Puth 같은 대형 해외 아레나 투어는 테스트 조회에서 나오지 않았습니다.
     즉 KOPIS는 "국내 콘서트/페스티벌 자동 보강용"으로 쓰고, 대형 해외 내한 공연은
     계속 `src/data/events.json`에 수동으로 추가하는 게 현실적입니다.
   - **키 관리 주의사항** (KOPIS 발급 안내문 기준):
     - 인증키 유효기간은 발급일로부터 1년, **3개월 이상 미사용시 자동 취소**됩니다.
       그래서 이 스크립트를 방치하지 말고 최소 몇 주~한 달 주기로는 실행되도록
       자동화하세요 (아래 "배포 전 체크리스트" 참고).
     - 유효기간 만료/취소 안내는 kopis@gokams.or.kr로 오며, 연장도 그 메일로 신청.
     - KOPIS의 "집계 데이터"(예매순위·관객수 통계 등)를 화면에 노출할 경우에만
       "집계기간/집계대상" 문구를 의무적으로 표기해야 합니다 - 지금은 일정 정보만
       쓰고 있어서 해당 없음. 다만 사이트 하단에 "데이터 출처: KOPIS" 크레딧은
       이미 넣어뒀습니다.
2. **수동 입력**: `src/data/events.json`에 직접 항목을 추가/수정하면 됩니다. 배열에
   객체 하나 추가하는 것뿐이라 어렵지 않습니다. KOPIS에 아직 안 올라온 따끈한 발표
   (막 공지된 내한 소식 등)는 당분간 이 방식으로 채우는 걸 추천합니다.

## Event 구조화 데이터 + 공식 링크 (2026-08-27)

각 공연 상세 페이지에 다음을 추가했습니다:

- **schema.org `MusicEvent` JSON-LD** — 구글이 검색결과에 날짜/장소를 리치 스니펫으로
  보여줄 수 있게 해주는 구조화 데이터. `name`/`startDate`/`endDate`/`location`/
  `description`/`performer`를 채워넣었고, `offers`(예매 링크)는 실제 `ticketUrl`이
  있는 이벤트에만 자동으로 붙습니다 — 없는 가격/재고 정보를 지어내지 않기 위함입니다.
- 처음엔 자체 생성 브랜드 카드 이미지(코드로 그린 placeholder)를 넣었었는데, 실제
  아티스트 사진/포스터가 아니라 정보 제공 목적에는 오히려 안 넣느니만 못하다고 판단해서
  **완전히 제거**했습니다. 이미지 대신 각 공연의 **공식 링크**(`ConcertEvent`의
  `ticketUrl` / `officialUrl` / `mdUrl` / `fanclubUrl`)를 상세 페이지에 버튼으로
  노출합니다 — 실제로 검색해서 확인한 링크만 넣었고, 확인 안 된 건 절대 추측해서 채우지
  않았습니다 (잘못된 링크는 없는 것보다 나쁨).
- 각 이벤트에 `description` 필드(2~3문장, 실제 아티스트/공연 정보 기반)를 채웠습니다.
- 지금은 대형 해외 내한 8건만 링크가 채워져 있고, KOPIS 소싱 10건은 아직 없습니다 —
  이어서 채워나가면 됩니다.

## J-pop 마이너 아티스트 자동 게시 파이프라인 (2026-08-30)

사이트 운영자 요청: "KOPIS에서 받아오는 J-pop 아티스트를 대형 공연장 급만 올리지 말고,
마이너/소극장 공연까지 전부 자동으로 올려줘." 기존 파이프라인은 `VENUE_CITY_MAP`(대형
공연장 화이트리스트)이 사실상 "이 정도 규모면 진짜 내한 공연이겠지"라는 필터 역할까지
겸하고 있어서, 소극장 J-pop 공연은 애초에 후보에 들지도 못했습니다.

**문제**: KOPIS API에는 국적/장르(J-pop 여부) 필드가 없습니다. `genrenm`은 홍대
인디밴드 공연이든 J-pop 내한이든 전부 그냥 "대중음악"으로만 옵니다.

**해결 방식** (일본어 문자 자동 감지 방식은 검토 후 기각 - "후지이 카제"처럼 완전히
한글로만 표기된 이름은 감지 불가):

- `scripts/jpop-artists.mjs`에 J-pop 아티스트 이름 화이트리스트(한글 표기 + 로마자/영문
  표기)를 만들어두고, KOPIS 원본 공연명(`prfnm`)을 이 목록과 매칭합니다
  (`fetch-kopis.mjs`의 `matchJpopArtist`).
- **매칭되면 `VENUE_CITY_MAP` 화이트리스트를 완전히 건너뛰고** — 아레나든 소극장이든 —
  `src/data/events.json`에 **바로 자동으로 씁니다** (PR/수동 복사 단계 없음). 도시는
  기존 `VENUE_CITY_MAP`에 있는 장소면 그 값을, 없으면 KOPIS 응답의 `<area>` 필드
  (예: "서울특별시" → "서울")로 채웁니다.
- 매칭 안 되면 기존 동작 그대로: `VENUE_CITY_MAP` 필터 통과한 것만
  `kopis-candidates.json`에 후보로 쌓이고, 사람이 손으로 골라 `events.json`에 옮겨야
  합니다. **이 파이프라인은 J-pop 매칭분에만 적용되고, 나머지 흐름은 안 건드렸습니다.**

**트레이드오프 (의도된 것)**: 자동 게시된 J-pop 항목은 KOPIS가 주는 최소 정보(아티스트/
장소/날짜/포스터)만 있고, 다른 공연들처럼 손으로 조사한 `description`/`funFacts`/
`sources`/`setlists`/`presale`/`youtubeVideos`는 비어 있습니다 (모두 선택 필드라 사이트가
깨지진 않지만, 페이지가 확연히 부실해 보일 수 있음). 각 항목의 `note`에 "자동 수집됨,
상세 정보 추후 보강 필요"라고 표시해뒀습니다. `jpop-artists.mjs`에 없는 신인/초마이너
아티스트는 자동으로 놓칠 수 있습니다 — 이건 정확도(허위 게시 방지)를 우선한 의도된
트레이드오프이며, 목록은 계속 늘려나가야 합니다.

**GitHub Action 반영 방식 (2026-08-30 업데이트)**: `fetch-kopis.yml`은 이제 변경사항이
있으면 PR을 여는 대신 **main에 바로 커밋 후 푸시**합니다 (J-pop `events.json` 자동 추가분
포함). 사이트 운영자가 명시적으로 결정한 사항 — 공연 정보 제공 페이지라 자동 추가된 공연이
검토 없이 바로 노출돼도 실질적인 리스크가 없다고 판단했습니다. 이전에는 `events.json` diff가
생길 때마다 PR을 열어 머지 전에 사람이 한 번 보게 했었는데, 그 방식을 원하면 다시 되돌릴 수
있습니다 (이전 워크플로우는 git 히스토리에 남아있음).

**2026-08-30 실제 검증**: 실제 KOPIS API로 6개월치(195건) 조회해서 파이프라인을 라이브
테스트했습니다. 아래 트러블슈팅 로그 5번 항목에 그 과정에서 잡은 오탐(false positive)
버그를 남겨뒀습니다. 이 실행 시점 기준으로는 화이트리스트에 매칭되는 신규 J-pop 공연이
0건이었습니다 (기존에 이미 올라간 오피셜히게단디즘/백넘버/Vaundy/Fujii Kaze 4건은 이미
`events.json`에 있어서 중복 제외됨) — 파이프라인 자체는 정상 동작하며, 다음 실행부터
새 공연이 매칭되는 대로 자동으로 쌓입니다.

## KOPIS 자동 수집 파이프라인 트러블슈팅 로그 (2026-08-27)

`.github/workflows/fetch-kopis.yml` + `scripts/fetch-kopis.mjs` 파이프라인을 만들고
안정화하기까지 실제로 겪은 문제와 원인, 고친 방법을 순서대로 남겨둡니다. 비슷한 증상이
다시 나오면 여기부터 확인하세요.

1. **너무 많은 노이즈 후보 (v1 → v2, commit `fe10215`)**
   증상: 첫 버전은 `events.json`에 직접 머지하는 PR을 열었는데, 한 번 실행에 후보가
   80건 가까이(diff 1,100줄+) 쏟아졌고 대부분 홍대 소극장/스튜디오 같은 소규모 공연.
   원인: KOPIS `shcate=CCCD`(콘서트) 카테고리는 등록된 공연을 전부 반환함 — 이
   사이트가 다루는 "해외 내한/대형 페스티벌" 급이 아닌 것도 다 섞여 옴. 게다가 id
   기준 중복 체크만 하다 보니 이미 있는 공연(예: ONEWE)이 다른 KOPIS id로 다시
   들어오기도 함.
   해결: `VENUE_CITY_MAP`(주요 공연장 화이트리스트)에 있는 장소만 후보로 남기고,
   (장소+날짜)/아티스트명 기준 중복 체크 추가, 결과를 `events.json`이 아니라
   `src/data/kopis-candidates.json`(사이트가 안 읽는 스테이징 파일)에 쓰도록 변경.

2. **고친 코드를 push해도 옛날 동작이 계속 반복됨**
   증상: v2로 고친 커�드를 push하고 `main`에서 워크플로를 다시 돌려도 여전히
   `events.json`에 1,000줄 넘는 diff가 나옴.
   원인: v1 실행 때 만들어진 `kopis-auto-update` 브랜치/PR이 남아있는 상태에서
   `peter-evans/create-pull-request`가 그 브랜치를 재사용하면서 옛날 상태가 계속
   반영된 것으로 보임 (완전히 확실하진 않지만, 브랜치를 지우고 나서 문제가 사라짐).
   해결: 남아있던 `kopis-auto-update` 브랜치를 GitHub에서 삭제하고 `main`에서 다시
   실행 → 그제서야 옛날 동작이 재현되지 않음.

3. **`rows=200`이 조용히 결과 0건을 만듦**
   증상: 브랜치 문제를 해결한 뒤 첫 실행에서 `KOPIS raw results: 0` — 필터가 너무
   빡빡한 줄 알았는데 사실 원본 조회 자체가 0건.
   원인: 스크립트를 고치면서 `rows`를 원래 검증됐던 `100`에서 `200`으로 늘렸는데,
   이 값은 실제 API로 테스트한 적이 없었음(개발 환경에서 kopis.or.kr 직접 접속이
   막혀 있어서). KOPIS가 `rows=200`을 에러 없이 그냥 빈 결과로 응답한 것으로 추정.
   해결: `rows: '100'`(검증된 값)으로 되돌리고, raw 결과가 0건이면 경고 로그를
   남기도록 추가 — 다음에 같은 문제가 나면 "필터 문제"가 아니라 "API 응답 문제"라는
   걸 로그에서 바로 구분할 수 있게.

4. **BEXCO(부산)가 대구로 잘못 분류됨**
   증상: 정상적으로 후보 7건이 나왔는데, "벡스코 (BEXCO)"가 열리는 공연의 city가
   `"대구"`로 찍힘.
   원인: `VENUE_CITY_MAP`에 대구 엑스코를 위해 넣어둔 영문 키 `'EXCO'`가, 부산
   벡스코의 영문 표기 `'BEXCO'` 안에 **부분 문자열로 포함**되어 있어서
   (`B` + `EXCO`) 문자열 포함 매칭 시 먼저 걸려버림. 전형적인 substring 매칭 함정.
   해결: 중복이던 영문 `'EXCO'` 키를 제거(한글 `'엑스코'` 키만으로 대구 엑스코는
   이미 잡힘). 앞으로 `VENUE_CITY_MAP`에 새 영문 약어를 추가할 땐 기존 키들의
   부분 문자열이 되지 않는지 확인할 것.

5. **J-pop 아티스트 이름 매칭이 무관한 단어 안에서 오탐 (2026-08-30)**
   증상: J-pop 자동 게시 파이프라인을 실제 KOPIS 데이터로 처음 라이브 테스트했을 때,
   "제18회 서울국제음악제, 아르토 노라스와 김규연 리사이틀" (클래식 첼로 리사이틀)이
   J-pop 아티스트 "LiSA"로 오매칭되어 `events.json`에 잘못 게시될 뻔함.
   원인: LiSA의 한글 표기 별칭 `'리사'`(2글자)가 "리사이틀"(recital)이라는 완전히
   무관한 단어 안에 부분 문자열로 포함되어 있었음. 영문 별칭은 단어 경계(word-boundary)
   정규식으로 보호했지만, 한글 별칭은 그런 보호 없이 단순 부분 문자열 매칭만 하고
   있었던 게 원인.
   해결: 한글 별칭의 최소 매칭 길이를 2글자에서 **3글자 이상**으로 올림
   (`matchJpopArtist`의 `normAlias.length >= 3`). 이 기준을 적용해도 목록의 모든
   아티스트가 최소 하나의(대부분 로마자) 대체 별칭으로는 계속 매칭 가능함을 스크립트로
   확인 후 적용 - 실제로 사라지는 매칭 경로 없음. 짧고 일상적인 한글 단어와 겹치는
   별칭(스캔들/심/야마/다우니/챠이/보리스/젝/세로/안리/미나미 등)은 애초에
   `jpop-artists.mjs` 작성 단계에서 제외했었는데, 2글자짜리(리사/아도/우루/밀레/에메
   등)는 놓쳤던 것 - 실제 라이브 데이터로 테스트하지 않았다면 발견 못 했을 케이스.

6. **`cpage`가 1페이지 뿐이라 결과의 대부분을 놓치고 있었음 (2026-08-30)**
   증상: J-pop 자동 게시 파이프라인을 실제 KOPIS 데이터로 처음 라이브 테스트했을 때
   (위 5번 항목 발견 당시), 6개월치 조회에서 J-pop 매칭 신규 공연이 0건이었음. 사이트
   운영자가 "API에 안 나오는 건지, 필터/데이터양이 부족한 건지" 정확히 짚어서 질문함.
   원인: `fetchKopisList`가 `cpage: '1'`만 요청하고 있었음 - KOPIS는 한 페이지에 최대
   `rows: '100'`건만 주는데(`rows=200`은 라이브로 재확인해도 여전히 조용히 0건 반환,
   에러 없음), 실제로는 같은 6개월 기간에 콘서트만 435건, 페스티벌 413건이 등록돼 있어서
   (직접 `cpage=2,3,4,5...`로 확인) 원래 1페이지(최대 100건)만 보고 있었던 건 전체의
   약 4분의 1도 안 됐음. J-pop 자동 게시가 원래 노리던 마이너/소극장 공연들이 애초에
   조회 대상에 들어오지도 못했던 것.
   해결: `fetchKopisList`가 `cpage`를 1부터 증가시키며 반환 건수가 `rows`(100)보다 적은
   페이지(=마지막 페이지)를 만날 때까지 반복 조회하도록 변경 (`MAX_LIST_PAGES = 30`
   안전장치 포함, 페이지 사이 200ms 딜레이). 재실행 결과: raw 737건(콘서트 457 +
   페스티벌 333, cross-dedupe 후)으로 4배 가까이 늘었고, 실제로 신규 J-pop 매칭 2건이
   나옴 (cero 홍대 라이브하우스 공연, T-Square 연세대 대강당 공연 - 둘 다 대형
   공연장 화이트리스트에는 없던 곳).
7. **위 6번 재실행에서 드러난 2차 문제 - 아티스트 중복 게시**
   증상: 6번 수정 후 재실행에서 J-pop 매칭 6건 중 진짜 신규는 2건뿐이고 나머지 4건은
   문제였음: (a) T-Square가 한글 제목("티스퀘어 라이브 인 서울...")과 영문 제목
   ("T-SQUARE Live in Seoul")으로 KOPIS에 각각 다른 `mt20id`로 두 번 등록돼 있어서
   둘 다 매칭돼 같은 공연이 두 번 게시될 뻔함. (b) 이미 손으로 `events.json`에 올려둔
   back number·Vaundy 공연이 KOPIS에 다른 장소 표기("킨텍스" vs "KINTEX",
   "인스파이어 엔터테인먼트 리조트" vs "인스파이어 아레나")로도 등록돼 있어서, 기존
   `existingArtistKeys`/`existingVenueDatePairs`의 문자열 완전일치 검사를 통과하지
   못하고 중복 게시될 뻔함.
   원인: 기존 중복 체크 3종 모두 "정확히 같은 문자열"을 요구함 - KOPIS 원본 제목은
   손으로 정리한 `events.json`의 짧은 `artist` 값과 문자열이 절대 똑같을 수 없고,
   같은 실제 장소도 KOPIS 안에서 여러 이름으로 등록될 수 있어서 이 검사들이 J-pop
   케이스에는 사실상 무력했음.
   해결: J-pop 경로 전용으로 **(정규화된 아티스트, 정확한 날짜)** 조합 키를 새로
   추가 (`existingJpopDates`) - `events.json`의 기존 이벤트들도 `matchJpopArtist`로
   한 번 돌려서 "이미 실린 아티스트+날짜" 집합을 만들고, 이번 실행에서 새로 추가하는
   항목도 즉시 그 집합에 추가해서 같은 실행 안에서의 중복도 잡음. 재실행 결과 정확히
   신규 2건만 게시됨.
   **교훈 추가**: 페이지네이션 문제는 "필터가 이상한가?" 방향으로만 의심했다면 못
   찾았을 것 - 사이트 운영자가 "데이터양 자체가 부족한 것 아니냐"고 명시적으로
   물어봐서 실제로 라이브 API를 다시 파고들어 확인한 덕분에 찾음. 이후 데이터 소스
   자체를 의심하는 질문은 항상 실제 페이지네이션/전체 건수부터 확인할 것.

**교훈**: 이 파이프라인은 개발 중 실제 KOPIS API에 접근할 수 없는 환경(샌드박스)에서
코드를 고쳤기 때문에, 로직을 아무리 꼼꼼히 짜도 실제 라이브 실행에서만 드러나는
문제(파라미터 검증, 데이터의 실제 형태)가 몇 차례 나왔습니다. `VENUE_CITY_MAP`을
더 추가할 때도 실제 실행 결과(Actions 로그 + PR diff)로 검증하는 걸 권장합니다.

## 이 프로젝트와 jpop-ai-blog의 관계

같은 profit_model 워크스페이스 안에 있는 `sites/jpop-ai-blog`(J-pop×AI 블로그)는
보류 상태입니다. 사용자가 "블로그보다 실용적인 도구/캘린더형 사이트"를 원해서 이
프로젝트로 방향을 틀었습니다. 두 프로젝트는 완전히 독립적인 Astro 앱이라 서로 코드를
공유하지 않습니다.
